Case Study 03Local AI Agent on a $0 Budget

Author: Jonas Bonnett
Published: October 26, 2026
Built: October 24, 2026 (one night session)
Stack: Ollama 0.40.10 + qwen3.5:4b (3.3 GB) + n8n 2.44.6, on an ASUS TUF laptop (Ryzen 5, 16 GB RAM)
Cost: $0 — no cloud account, no paid API key, no subscription

The problem

Wanted a private AI assistant that runs entirely on his own laptop — no data leaving the machine, no monthly fee, no dependence on a cloud provider — with real agent behavior: memory, tools, and a workflow engine, not just a chatbot window.

What was built

A published n8n workflow (“Jdogg Rockstar”) wired to a local language model:

  • Chat Trigger → AI Agent → Edit Fields (output passthrough) → chat reply
  • Agent sub-nodes: Ollama Chat Model (qwen3.5:4b) + Simple Memory (context window 5) + Calculator tool + Wikipedia tool
  • System prompt: a local assistant running on his laptop via Ollama, not a cloud service

How it was proven (tests, all passed)

  • Local proof: Wi-Fi turned OFF — the model still answered. Computation is on the laptop, not in the cloud.
  • Agent run: Chat message through n8n to the local model and back — “AI Agent Success,” ~12 seconds, ~76 tokens.
  • Memory: Told it “My name is Jdogg Rockstar,” then asked “What is my name?” — it answered “Your name is Jdogg Rockstar!”
  • Tool use (math): “What is 247 times 38?” — answered 9386, exact, via the Calculator tool.
  • Tool use (facts): “Look it up on Wikipedia: how many islands are in the Philippines?” — answered ~7,641, quoting real fetched article text.
  • Output chain: Edit Fields pass-through executed clean; the chat reply carried the answer end to end.
  • Published: workflow flipped to Active — the agent runs on its own, no editor needed.

Problems solved along the way

  • n8n was installed but not running (it does not auto-start on boot) — restarted from the terminal.
  • n8n’s newer editor redirects to a paid Assistant page — dismissed it; the Assistant needs a paid API key and was skipped under the $0 rule.
  • The Ollama connection first failed with ECONNREFUSED even though Ollama was running — root cause was Windows resolving localhost to IPv6 while Ollama listens on IPv4. Fix: Base URL http://127.0.0.1:11434.
  • Open WebUI could not install: it requires Python 3.11/3.12 and the laptop has 3.13; Docker was not installed. Deferred honestly instead of forcing it — the Codex app already served as the local chat window.

Honest limits (stated, not hidden)

  • The 4B model is slow (~1 minute for long answers) and its identity answers are unreliable — asked where it runs, it sometimes repeats its factory cloud story or emits a stray tool-call code. That is a small-model limitation, documented, not a setup failure.
  • A second local model (llama3.2:latest, 2.0 GB) is already on the machine for future comparison tests.

Skills this demonstrates

Local LLM deployment and model selection for constrained hardware, workflow automation, systems integration across three separate tools, methodical troubleshooting (port conflicts, IPv6 vs IPv4, version constraints), and shipping a working system on a zero budget in a single session.

What this is not

This is not a claim of cloud-scale AI expertise, and no employer-facing version of this document should imply one. It is proof of a real, working, local system built by hand — verifiable by running it on the laptop.
